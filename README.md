Plenty of apps say they work locally. Nothing checks. `stays local` is the check: your source is built in this repository's CI, the artifact is scanned for any way to reach the network, and the app is run and watched. Pass, and you get a badge generated by the run that earned it.

## Platforms

| Platform | Spec | Verifier | Evidence it rests on |
|---|---|---|---|
| **macOS** | [stable](spec/macos.md) | [done](verifiers/macos/verify.sh) | No binary in the bundle names `URLSession`, sockets, … |
| **Android** | [stable](spec/android.md) | [done](verifiers/android/verify.sh) | The OS refuses sockets without `INTERNET` |
| **Windows** | [draft](spec/windows.md) | [wanted](https://github.com/2JIHAN/stays-local/labels/verifier) | No PE imports `WS2_32`, `WINHTTP`, … |
| **iOS** | [draft](spec/ios.md) | [wanted](https://github.com/2JIHAN/stays-local/labels/verifier) | Symbol references — linkage proves little here |

Platforms are not interchangeable, and the badge should not pretend otherwise. Android's badge is the strongest available: without the `INTERNET` permission the kernel refuses the socket, so the property is *enforced* rather than inferred. macOS is inferred from the symbols a binary names. iOS is the weakest, because `UIKit` drags `CFNetwork` in on every app and the linkage check loses its teeth.

## What passing means

**The app's shipped code contains no way to reach the network.** That is the whole claim, and it is narrow on purpose, because it is the part that can actually be checked.

Each platform defines its own layers; see its spec. A layer is `required` (failing fails the badge), `conditional` (required when it can run, skipped and noted when it cannot — the runtime layers), or `recorded` (published but not decisive).

On macOS the load-bearing layer is the symbol scan, not the linkage check. Naming `URLSession` or a socket call leaves the name in the Mach-O; linking `CFNetwork` does not reliably happen, because `Foundation` exports `NSURLSession` itself. That correction is written up in [`proposals/0001`](proposals/0001-layer-statuses.md).

## What it does not mean

| Not covered | Why |
|---|---|
| Code the app shells out to | `curl` in a script is invisible to a binary scan |
| IPC to another process | The app can ask a service that does have network access |
| Files written for another app to upload | Nothing leaves *this* process; something else may carry it |
| Code loaded at runtime | A plugin is not in the artifact we checked |
| **Data smuggled in a declared URL** | Unsolved. See [known gaps](spec/core.md#known-gaps) |
| The binary you downloaded | We check a build from public source, not your download |

It is one checkable property, not a privacy audit. Say so when you cite it.

[`bypasses/`](bypasses/) is the public, executable catalogue of ways around it, and it does not flatter us: **three of five known macOS bypasses succeed today.** Two are inherent to scanning one process's binary — an app can shell out to `curl`, or hand data to a helper over XPC — and the third is the declared-URL gap. CI runs the corpus on every push, so a verifier that stops catching one goes red.

## Apply

1. Add `stays-local.json` to your repository root:

```json
{
  "name": "Your App",
  "platform": "macos",
  "repository": "https://github.com/you/your-app",
  "build": "./build.sh \"$STAYS_LOCAL_OUT\"",
  "bundle": "Your App.app",
  "declared_urls": []
}
```

2. Run the check yourself first:

```bash
git clone https://github.com/2JIHAN/stays-local.git
./stays-local/verify.sh /path/to/your-repo --runtime
```

3. [Open an application issue](https://github.com/2JIHAN/stays-local/issues/new?template=apply.yml).

The check then runs here, on a fresh checkout of your public source, and the log is public. You do not certify yourself, and no maintainer can wave you through — [the run decides](GOVERNANCE.md#certification-is-not-a-judgement-call).

## Use the badge

Your badge is generated by the run that certified you and lives here, so it is not a picture you host and control.

```markdown
[![stays local](https://raw.githubusercontent.com/2JIHAN/stays-local/main/badges/YOUR-SLUG.svg)](https://github.com/2JIHAN/stays-local#registry)
```

The badge carries the date it was earned — `verified 2026-08-09`, not just `verified`. A claim about software should show its age, and one that quietly goes stale is worth less than one that visibly does.

`registry/YOUR-SLUG.json` holds the same result in machine-readable form: which layers passed, what was declared, and a link to the run.

> [!IMPORTANT]
> **Only macOS and Android can be certified today.** Windows and iOS have written specs and no verifier, so there is nothing to earn a badge from yet — the entries in the platform table above say `wanted`, not `available`. If you want one for those platforms, the fastest route is [writing the verifier](CONTRIBUTING.md); it is the thing the project most needs and it makes you that platform's maintainer.

## Contributing

**Contributions are welcome, and two platforms are wide open** — Windows and iOS. Both have a written spec and no code, so there is nothing to reverse-engineer: the layers are described, the open design questions are listed, and you are expected to argue with them before writing anything. Landing a verifier makes you that platform's maintainer.

Neither is certifying apps yet, so nothing depends on you getting it right the first time. That is the easiest a project of this kind will ever be to join.

**Bypasses are the other half.** [`bypasses/`](bypasses/) is a corpus of apps that reach the network while passing layers. Adding a case that current verifiers miss is arguably a better contribution than a feature — it is the thing that keeps the badge from becoming decoration.

Read [CONTRIBUTING.md](CONTRIBUTING.md). Criteria changes carry a higher bar than code changes, because they change what every existing badge means, retroactively — that split is written down in [GOVERNANCE.md](GOVERNANCE.md).

If you have a working bypass, read [SECURITY.md](SECURITY.md) before opening it in public. Every certified app is affected until it is fixed.

## Staying honest

The badge carries the date it was earned, and the registry entry links to the run that earned it. A claim about software that shows its own age cannot go quietly stale.

Re-verification is deliberate rather than scheduled. Building an applicant's current source on a timer would mean an app certified while benign could swap in a malicious build later and have it executed automatically, every week, with nobody deciding to — a poor trade for a scheme whose own runner is the thing an attacker would most want. A maintainer re-runs the check on request or when something looks wrong, and a weekly job flags entries nobody has looked at in 90 days without building anything.

The badge you embed is still the one this repository generates, so it cannot be edited into saying something the check did not.

Closed-source apps cannot be certified. The check needs to build from public source, and a claim you cannot inspect is the thing this is meant to replace.
